## 1. 证明了什么 / 只是观察到什么 / 还不知道什么

**证明了**（有干预实验与因果链）：R02 的旧结论由缓存键缺失（仅含 query）引起——
新鲜实例输出正确、原顺序精确复现、源码键行确认，三点闭合；R03 的证据丢失由
"全库排序先于范围过滤"独立引起（无缓存参与仍复现）。

**只是观察到的**：R04 的语义冲突由"ID有效即supported"造成（代码事实 + 原文对照），
本修复用轻量规则（数值定位 + 限定词）将其降为 insufficient——该规则在 7 案上与人工
判断一致，但**未在开放语料上验证**；R07 的 invalid_scope 缺失为代码事实，修复行为符合
spec#1 的字面要求，但"未知组合"的其他形态（未知 snapshot、空 doc_ids）未逐一构造。

**还不知道的**：修复引擎在题包之外的真实文档上的泛化；轻量语义规则的误报/漏报率；
样机的确定性是否会在时间相关实现（如 TTL 缓存）中变成概率行为。

## 2. 接到当前项目需要增加的日志/状态字段

在现有 request_id / cache_hit / run_kind 之外，接入真实项目时应补：
- `scope_digest`：本次 doc_ids+snapshot 的散列，随响应落盘，使"用错快照"可被审计；
- `support_basis` + `checker_version`（本修复已有 basis，需补版本号），支持判定策略回溯；
- `cache_key_fields`：实际参与缓存键的字段列表，防止键维度再次被无意裁剪；
- 请求生命周期时间戳（提交/入队/开始推理/完成），把"耗时"拆成可归因的阶段。

## 3. 多用户/多 worker 环境下会失效的假设

样机是**单进程内存状态**：缓存与引擎实例挂在进程上，"reset 清空即状态一致"只在
单实例成立。多 worker 下会失效的是：①各 worker 缓存互不可见 → 同请求可能得到
不同 cache_hit 与不同代次的结果；②reset 只清一个 worker → 资料版本切换后旧 worker
仍能返回旧结论（R02 的故障会在集群尺度重现）；③内存缓存无淘汰策略 → 多用户下
成为无界增长的资源问题。此外需区分：**应用层缓存复用**（可接受等价输入）≠
**排队等待**（用户可感知延迟）≠ **逻辑取消**（请求被拒绝但计算可能仍在跑）≠
**真正释放推理资源**（GPU 槽位归还）——四者在样机中都不存在，不能宣称已测。

## 4. 可执行验证方案与停止条件

**方案**：起 2 个 worker 进程 + 一个最小代理，脚本顺序发 R01→R02（不同 snapshot、
相同 query），断言两侧返回的 evidence.snapshot 均等于各自请求的 snapshot；再注入
"运行中取消"请求，观测取消后 GPU 占用是否在 T 秒内归还（`nvidia-smi` 轮询）。

**停止条件**（任一即停）：
- 200 次顺序请求中出现 1 次 snapshot 串代 → 停止并登记为多 worker 缓存隔离缺陷；
- 取消后 10 秒内资源占用未下降 → 停止，登记"逻辑取消≠资源释放"；
- 全部通过 → 记录配置与日志样本，作为接入项目的前置验收，不扩展为分布式系统开发
  （超出本周任务范围）。
