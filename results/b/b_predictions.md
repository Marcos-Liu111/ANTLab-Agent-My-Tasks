## 主问题选择

**R02：换了资料版本却显示旧结论。** 理由：直接给出错误事实（30秒 vs 12秒），
是四个症状中对用户任务伤害最直接的一个；且有明确的机器可查证据（cache_hit=True）。

## 两个仍与已有证据相容的解释（H1 vs H2）

- **H1（缓存污染）**：`challenge.py` 缓存键只有 `request['query'].strip().lower()`，
  不含 doc_ids/snapshot/k。R01 的 v1 结果被 R02 的 v2 请求命中复用。
- **H2（排序先于范围过滤）**：`selected = ranked[:k]` 在**全库**排序后截断，
  再过滤 scope。R02 即使不命中缓存，v1 的 b01（同分但 id 更小）也可能挤掉 v2 的 b02，
  导致返回 v1 材料。（同机制已在 R03 中独立可见：k=1 名额被 scope 外的 b01 占走。）

## 各自的可观察预测（先于实验写下）

| 实验 | H1 预测 | H2 预测 |
|---|---|---|
| **E1**：全新 Engine 实例只跑 R02（不先跑 R01） | answer=**12秒**、evidence=[b02]、cache_hit=False → **H1 成立** | 若仍返回 30秒/b01 → H1 不成立、H2 成立 |
| **E2**：全新实例只跑 R03（k=1, doc=beta） | 与 H1 无关（R03 无缓存参与）：evidence 应含 **b03**（若无 H2 缺陷） | 若 evidence 仍为空 → **H2 独立成立**（与缓存无关） |
| E3（辅证，反向因果检查）：核对 R02 的 draft 原文 | draft 本身写的是 12秒/b02 → 错误来自引擎/缓存，而非 draft 侧 | 同左 |

**判别逻辑**：E1 若返回 12秒 → R02 归因 H1（缓存键缺失），H2 对 R02 不成立；
E1 若返回 30秒 → H1 被推翻，R02 归因 H2。E2 用于判断 H2 是否独立存在（与 R02 分离）。

## 反向因果/评价错误检查（预先选定）

- C1：R02 耗时短（缓存命中路径）是否能被解释为"处理更快"而非"走了缓存"？
  → 检查 cache_hit 字段与 elapsed_ms 的对应；不能用耗时差异证明功能正确。
- C2：R04 的 supported 减少是否可能来自"全部 not_checked"？
  → baseline 中 R01/R05/R06 为 supported，非全量保守，排除该解释。

## 预期的修复方向（干预前意向，非结论）

若 E1/E2 如预测：最小修复 =（a）缓存键纳入 doc_ids+snapshot+k（或按 spec#5 选择关闭缓存）；
（b）范围过滤先于取 k。两者分别对应 H1/H2，均不动 Engine 接口。
语义支持（R04）与 invalid_scope（R07）风险另案登记，不混入主问题。
